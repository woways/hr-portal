1. Executive Summary

The WOWAYS HR Portal is an enterprise-grade Human Resource Management System (HRMS) delivered as two connected web applications sharing a single Firebase backend. It digitises the complete employee lifecycle — from recruitment and onboarding through attendance, leave, payroll, performance and offboarding — while giving employees a self-service portal for their personal data, attendance, leave, payslips and goals.

Two applications, one source of truth:
• HR Admin Dashboard — the control centre used by HR administrators to manage the entire workforce.
• Employee Self-Service Portal — a focused portal where employees view and update their own information.
Both apps read/write the same Firebase project, so every change is reflected across the system in real time.

5. HR Admin Dashboard — Functional Requirements

5.1 Dashboard / Overview

  • KPI cards: total employees, interns, active, on probation, on leave, exited.
  • Attendance overview: present, absent, late logins, half-day, average working hours (today).
  • Leave summary (pending / approved / rejected) and goal completion breakdown.
  • Charts: department-wise headcount, 6-month leave trends, monthly hiring trend.
  • Live clock and personalised welcome header.

5.2 Employee Directory /dashboard/employees

  • Add, edit, view and delete employees via a multi-tab form (personal, employment, statutory, education, documents).
  • Auto-generated employee IDs (EMP001, EMP002 …) and automatic Firebase Auth account creation with generated credentials.
  • Profile photos, searchable/filterable list by department, bulk CSV/Excel import, and export.
  • HR-managed document uploads (offer letters, internship letters) per employee.

5.3 Attendance & Time /dashboard/attendance

  • Daily attendance logs, live clock-in/out records and regularisation requests.
  • Status tracking: Present, Absent, Half-Day, Late, Week Off; working-hours calculation.

5.4 Leave Management /dashboard/leave

  • Real-time queue of leave requests with approve / reject actions.
  • Leave types (Casual, Sick, Emergency), medical-proof attachments, and status sync back to the employee.

5.5 Payroll & Compensation /dashboard/payroll · /compensation

  • Salary table, monthly payroll runs, CTC management and incentives.
  • Payslip generation available to employees for download.

5.6 Recruitment & Hiring /dashboard/recruitment · /hiring

  • Candidate pipeline / applicant tracking (ATS), job postings and sourcing channels.

5.7 Performance & Goals /dashboard/goals · /performance

  • Assign goals/KPIs, track status (Not Started, In Progress, On Track, At Risk, Completed) and record performance reviews.

5.8 Onboarding, Documents, Reports & Admin

  • Onboarding — new-hire checklists.
  • Documents — central document repository.
  • Reports & Analytics — workforce analytics and exports.
  • Admin & Access — role assignment and access control.
  • Notifications — company-wide and targeted announcements.
  • Help & Support — employee query inbox.
  • Settings — organisation configuration, holidays.

8. Authentication & Authorization

  • Auth method: Firebase Email/Password with local persistence.
  • Account provisioning: HR creates an employee → a Firebase Auth account is generated with credentials, and a users/{uid} document links the UID to the employee ID.
  • Identity resolution: The system resolves an employee's Firestore record by email lookup (most reliable) with a fallback to users/{uid}.employeeId.
  • Role-based rules: Firestore security rules enforce that employees access only their own leave/payroll/profile data, while HR admins (identified by a role claim / users-doc role) have broader access. All access requires authentication.
  • Storage rules: Profile photos, documents, certificates and attachments are readable/writable only by authenticated users.

10. Caching & Performance Strategy

  • Session cache: Frequently viewed lists (e.g. employees) and sidebar identity are cached in sessionStorage and rendered immediately on load.
  • Cache-then-network: The cached service returns a cached value first (instant paint), then re-fetches from Firestore and updates both the UI and the cache.
  • Skeleton components: Dedicated skeleton loaders (header, stat grid, chart, card) prevent layout shift during first fetch.
  • Cache invalidation: Any create/edit/delete re-runs the loader, which rewrites the cache, so it never goes stale.

12. Deployment & Infrastructure

  • Build: Next.js static export (next build → out/) for each app.
  • Hosting: firebase deploy --only hosting deploys both sites from the HR dashboard directory (multi-target config).
  • Sites: HR → hrmanagement-6b903.web.app; Employee → woways-employee.web.app.
  • Config: Firebase credentials injected via NEXT_PUBLIC_* environment variables; both apps use the same project.
  • Rules deployment: Firestore and Storage rules versioned in the repo (firestore.rules, storage.rules).

13. Assumptions, Constraints & Future Scope

Assumptions

  • Single organisation (WOWAYS); one Firebase project per deployment.
  • Employees receive credentials created by HR; email/password is the only auth method.

Constraints

  • Static export — no server-side rendering or server API routes; all logic runs client-side against Firebase.
  • Statutory features (PF/tax) are record-keeping, not a certified payroll engine.

Future Scope

  • Push/email notifications, biometric/geo attendance, mobile app.
  • Advanced analytics & AI insights, multi-tenant support, SSO.
  • Automated payslip PDF generation and statutory filing exports.
